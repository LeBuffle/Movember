# Story 11.5 : Sauvegardes automatisées et restauration testée

## Status

Review

## Story

**As a** porteur du projet,
**I want** pouvoir restaurer la base,
**so that** une erreur de notre part ne soit pas la fin de l'édition.

## Acceptance Criteria

1. Une sauvegarde quotidienne indépendante de Supabase.
2. Une sauvegarde vide ne remplace jamais la dernière bonne.
3. Sept copies conservées, puis rotation.
4. La sauvegarde passe **avant** la purge de la story 11.4.
5. Le mot de passe de la base n'est jamais dans le dépôt.
6. La procédure de restauration est écrite **et répétable**.

## Dev Notes

Le critère de sortie de l'epic n'est pas « une sauvegarde est configurée », c'est **« une
sauvegarde a été restaurée »**. Cette story fournit ce qu'il faut pour que cette phrase soit
vérifiable ; la vérification elle-même appartient au PO.

### Testing

- `backup-database.sh --check`, puis une restauration dans une base d'essai.

## Dev Agent Record

### Décisions prises

**Pourquoi une sauvegarde à nous alors que Supabase en fait déjà.** Les leurs couvrent une
panne de Supabase. Elles ne couvrent pas **nos** erreurs : une migration qui supprime la
mauvaise colonne, une purge à la mauvaise date sont des opérations valides, répliquées
instantanément. Seule une copie d'avant les rattrape. Et surtout : une sauvegarde Supabase
ne se restaure que dans le projet Supabase — impossible de **répéter** une restauration,
donc impossible de satisfaire le critère de sortie.

**Le dump est écrit sous un nom temporaire, et renommé seulement après contrôle de taille.**
La façon classique de tout perdre n'est pas de ne pas sauvegarder : c'est une sauvegarde
cassée qui remplace silencieusement la dernière bonne, chaque nuit, pendant un mois. Un dump
sous 20 Ko n'est pas une base, c'est un message d'erreur, et il est refusé.

**La rotation vient après un dump réussi, jamais avant.** Supprimer les anciennes d'abord
ferait qu'une nuit en échec ne laisse plus rien.

**La sauvegarde à 3 h 12, la purge à 4 h 34, et cet ordre est vérifié par un test.** Une
sauvegarde prise après la purge serait la sauvegarde de l'état déjà purgé : une purge à la
mauvaise date deviendrait irrécupérable depuis la sauvegarde censée la couvrir. Le test lit
les deux heures dans le crontab et compare — parce que c'est le genre de détail qu'un
réarrangement du fichier casse sans bruit.

**`--no-owner --no-privileges` sur le dump.** Les rôles d'un projet Supabase n'existent pas
dans la base où l'on restaure pour répéter, et leur absence transformerait la restauration
en mur d'erreurs de permissions — donc en répétition abandonnée.

**`--clean --if-exists`**, ce qui rend le dump applicable sur une base déjà peuplée. C'est
aussi ce qui le rend dangereux, et le runbook le dit à cet endroit précis.

**La chaîne de connexion contient le mot de passe de la base.** Elle vit dans `deploy/.env`
en chmod 600 sur le serveur. Un test balaie tous les scripts de `deploy/scripts/` et échoue
si une URL Postgres avec mot de passe y apparaît un jour.

### Ce que cette story ne fait pas

- **Pas de copie hors du serveur.** Une sauvegarde sur la même machine ne couvre pas la
  perte de la machine. Un envoi vers un stockage externe est un coût récurrent et une clé de
  plus à garder : à trancher par le PO, et le runbook le signale.
- **Pas de restauration automatisée.** Une restauration écrase des données. Un script qui
  la lancerait seul est un script qui peut détruire une édition.
- **Pas de sauvegarde du stockage des visuels.** Les images de cartes vivent dans Supabase
  Storage et sont reproductibles depuis les originaux du PO.

### Reste à faire — action PO

1. **Installer le client Postgres** sur le VPS : `apt install -y postgresql-client`.
2. **Renseigner `DATABASE_URL`** dans `deploy/.env` (Supabase → Project Settings → Database
   → Connection string → URI, connexion **directe**, pas le pooler), puis `chmod 600`.
   ⚠️ Cette chaîne contient le mot de passe : elle ne se colle que sur le serveur.
3. **Lancer une première sauvegarde à la main** :
   `sudo bash /opt/defi-movember/deploy/scripts/backup-database.sh`
4. **Répéter une restauration** dans une base d'essai, en suivant `docs/runbook.md` §13.
   ⚠️ Jamais sur la base de production. **C'est le critère de sortie de l'epic 11.**
5. **Trancher** : veut-on une copie hors du serveur ? Coût récurrent contre survie à la
   perte du VPS.
