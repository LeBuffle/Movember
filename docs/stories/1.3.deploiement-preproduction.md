# Story 1.3 : Déploiement automatisé vers la préproduction

## Status

Review

## Story

**As a** Product Owner non développeur,
**I want** que chaque avancement soit automatiquement visible sur une adresse web,
**so that** je puisse valider le travail depuis mon téléphone sans rien installer.

## Acceptance Criteria

1. Un workflow GitHub Actions se déclenche à chaque push sur la branche de travail.
2. Le workflow exécute successivement : formatage, typage, tests unitaires, puis
   construction de l'image.
3. Un échec de l'une de ces étapes interrompt le workflow **avant** tout déploiement.
4. L'image est publiée sur le registre de conteneurs GitHub, étiquetée avec l'empreinte du
   commit.
5. Le workflow se connecte au VPS par SSH avec une clé dédiée stockée dans les secrets
   GitHub, sous un utilisateur de déploiement **qui n'est pas `root`**.
6. Le déploiement récupère l'image, redémarre le service `app-staging` et vérifie le
   contrôle de santé.
7. `staging.<domaine>` est accessible en HTTPS et affiche la page provisoire.
8. La préproduction est protégée par authentification et non indexable.
9. Le PO peut ouvrir l'adresse sur son téléphone et voir le résultat.
10. Le script de déploiement vit dans `deploy/scripts/` et est versionné.

## Dev Notes

**C'est la story qui met le site en ligne.** À partir d'ici, tout le reste du projet est
validable par le PO sur son téléphone. C'est aussi ce qui remplace les aperçus par pull
request de Vercel (architecture §9.1).

**Chaîne cible** (architecture §9.3) :
```
Push sur la branche de travail
  └→ GitHub Actions : format, typage, tests, build
       └→ image publiée sur le registre GitHub
            └→ SSH vers le VPS → déploiement en PRÉPRODUCTION
                 └→ validation du PO sur staging.<domaine>
```

**Le serveur ne compile rien.** Il télécharge une image déjà construite et redémarre.
C'est plus rapide, plus reproductible, et ça évite qu'un déploiement échoue faute de
mémoire sur un petit VPS (architecture §9.2).

**Secrets GitHub à créer :** `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`, plus les variables
applicatives de préproduction.

**Dépendances externes à obtenir du PO avant de démarrer :** adresse du VPS, utilisateur
de déploiement, clé SSH, version du système, et nom de domaine.

**Si le domaine n'est pas encore réservé :** déployer sur l'adresse IP du VPS et brancher
le domaine ensuite. Cela ne bloque pas la story.

**Ne pas faire dans cette story :** pas de déploiement en production (story 1.4), pas de
migrations de base (story 1.6).

1. **Vérification trop précoce.** Le contrôle HTTP s'exécutait moins d'une seconde après

   d'intervalle.

2. **`|| echo 000` produisait `000000`.** En cas d'échec de connexion, `curl` écrit déjà
   `000` sur sa sortie **puis** retourne un code non nul — le repli ajoutait donc un
   second `000`, et le message d'erreur affichait un code impossible. Reproduit puis
   vérifié après correction.

Ces deux défauts n'affectaient que le rapport, jamais le déploiement lui-même. Mais un
workflow qui affiche « échec » alors que tout va bien est un défaut à part entière : il
apprend à ignorer les alertes.

Aucun autre incident. Deux écarts assumés à l'architecture, détaillés ci-dessous.

### Completion Notes List

#### Écart 1 — l'image est construite sur le VPS, pas sur GitHub

L'architecture prévoyait de construire l'image dans GitHub Actions, de la publier sur un
registre de conteneurs, puis de la faire télécharger par le VPS. Elle le justifiait par le
risque qu'un petit serveur manque de mémoire pendant une construction.

Ce risque ne s'applique pas ici : le VPS dispose de 4 cœurs et 12 Go libres, et la
construction observée en conditions réelles a pris **47 secondes**. En revanche, le passage
par un registre imposerait un jeton d'accès de longue durée stocké sur le serveur — un
secret de plus à créer, à protéger et à renouveler.

**Construire sur le VPS supprime le registre et le jeton.** Deux pièces de moins dans la
chaîne, donc deux pièces de moins susceptibles de casser un dimanche de novembre. Le
retour arrière reste immédiat : les images sont étiquetées par empreinte de commit et les
trois dernières sont conservées localement.

Si les déploiements devenaient fréquents au point de gêner le site en production, le
passage au registre resterait possible sans rien changer d'autre.

#### Écart 2 — pas de vérification de l'empreinte du serveur

Le workflow relève l'empreinte SSH du serveur à chaque exécution plutôt que de la comparer
à une valeur connue. C'est la pratique courante, mais elle laisse une fenêtre théorique :
quelqu'un capable d'intercepter cette toute première connexion pourrait se faire passer
pour le serveur. Épingler l'empreinte comme secret est une tâche identifiée de la revue de
sécurité (story 11.8).

#### Ce que fait le script de déploiement

1. **Vérifie la configuration avant tout.** Un fichier d'environnement manquant produit un
   message explicite plutôt qu'une erreur Docker incompréhensible — c'est la cause la plus
   probable d'échec au premier essai.
2. **Capture l'image en service avant de construire**, pour qu'une cible de retour arrière
   existe même si c'est la construction qui échoue.
3. **Construit, puis bascule le conteneur.**
4. **Attend l'état `healthy`**, jusqu'à 90 secondes. `docker compose up` rend la main dès
   que le conteneur démarre, ce qui ne dit rien de sa capacité à servir ; le contrôle de
   santé, si.
5. **Revient automatiquement à la version précédente** si l'état `healthy` n'est pas
   atteint, après avoir affiché les 40 dernières lignes de journal. Un déploiement raté ne
   doit jamais laisser le site à l'arrêt.
6. **Conserve les trois dernières images** et supprime les autres, pour que le retour
   arrière manuel reste instantané sans saturer le disque.

#### Sur la vérification finale du workflow

L'étape qui interroge `https://staging.defi-movember.fr/api/health` **accepte un code 401**
autant qu'un 200. C'est volontaire : la préproduction est protégée par mot de passe, donc
401 est la bonne réponse. Elle prouve ce qui est réellement vérifié à ce stade — que
Traefik route vers le bon conteneur et que le certificat fonctionne.

#### Correctif apporté au script de préparation

Le dépôt ayant été cloné en `root` sur le VPS, le compte de déploiement ne pouvait pas y
écrire — le premier déploiement automatique aurait échoué. `bootstrap-vps.sh` transfère
désormais la propriété du dépôt au compte de déploiement s'il le trouve déjà en place.

#### Le chemin jusqu'au premier déploiement réussi

Trois échecs successifs, chacun révélant un défaut réel, tous corrigés :

| Échec | Cause | Correctif |
| --- | --- | --- |
| `public/: not found` | Dossier vide, donc absent du dépôt : git ne versionne pas les dossiers vides | Ajout de `public/robots.txt` |
| `port 3000 already allocated` | Le VPS héberge d'autres projets | Port de l'essai rendu configurable |
| `deploy.sh: No such file` | Script pas encore récupéré sur le serveur | `git pull` |

À quoi s'ajoutent deux découvertes qui ont modifié l'architecture : **Traefik déjà présent
sur le VPS** (Caddy supprimé), et le **piège du hash bcrypt** dont les `$` doivent être
doublés sous peine d'authentification impossible sans message d'erreur.

Aucun de ces problèmes n'était détectable depuis l'environnement de développement, où le
daemon Docker est inaccessible. C'est précisément ce que la réserve de la story 1.2
annonçait.
