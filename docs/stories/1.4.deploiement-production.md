# Story 1.4 : Déploiement en production et retour arrière

## Status

Review — le mécanisme est livré ; la mise en ligne effective demande le feu vert du PO

## Story

**As a** Product Owner,
**I want** que la mise en production soit automatique et réversible en moins d'une minute,
**so that** une mise à jour ratée en plein mois de novembre ne mette pas le jeu à l'arrêt.

## Acceptance Criteria

1. Une fusion dans `main` déclenche le déploiement en production.
2. Les migrations de base de données sont appliquées **avant** la bascule des conteneurs.
3. Un échec de migration interrompt le déploiement sans toucher aux conteneurs en service.
4. Après la bascule, un contrôle de santé vérifie que l'application répond.
5. Si le contrôle de santé échoue, le déploiement revient automatiquement à l'image
   précédente.
6. Un script `deploy/scripts/rollback.sh` permet un retour arrière manuel vers la version
   antérieure en une commande.
7. Les trois dernières images sont conservées sur le serveur et identifiables.
8. Le domaine de production est accessible en HTTPS, sans authentification.
9. Le cron système du VPS est installé depuis `deploy/crontab` par le script de
   déploiement.
10. Une entrée de cron d'exemple fonctionne et appelle une route protégée par
    `CRON_SECRET`.

## Dev Notes

**Séquence de déploiement en production** (architecture §9.3) :
```
squash merge dans main
  └→ GitHub Actions : build + image « production »
       └→ SSH vers le VPS :
            1. migrations de base appliquées
            2. nouvelle image récupérée
            3. bascule des conteneurs
            4. contrôle de santé
            5. retour à la version précédente si échec
```

**Le retour arrière est le filet de sécurité indispensable** quand on déploie en plein mois
de novembre (architecture §9.3). Il doit être testé dans cette story, pas découvert le jour
où on en a besoin.

**Convention de migrations** (architecture §9.3) : les migrations sont versionnées dans
`supabase/migrations/` et appliquées avant la bascule. **Une modification de schéma faite à
la main dans l'interface Supabase serait perdue au déploiement suivant : c'est interdit par
convention.**

**Tâches planifiées** (architecture, décision D7) : le cron système du VPS appelle des
routes protégées de l'application. Le fichier `deploy/crontab` est versionné dans le dépôt
et installé par le script de déploiement, pour éviter qu'il diverge silencieusement.

Les tâches réelles seront ajoutées par les epics suivants :
attribution quotidienne des défis (epic 4), rattrapage Strava (epic 3), rafraîchissement
des classements (epic 7), sauvegardes (epic 11).

**Ne pas faire dans cette story :** pas de tâches planifiées métier, seulement le
mécanisme et une route de vérification.

## Dev Agent Record

### Écarts assumés par rapport au plan initial

**1. Les migrations sont appliquées depuis GitHub Actions, pas depuis le VPS.**
La story prévoyait la CLI Supabase sur le serveur. Elle tourne en réalité sur le
coureur GitHub, dans un job distinct placé **avant** celui du déploiement. Deux raisons.

La première est que c'est ce qui satisfait vraiment l'AC 3 : un job qui échoue arrête la
chaîne, et le job de déploiement ne démarre jamais. Les conteneurs en service ne sont pas
touchés, le site reste debout sur la version précédente — ancien code contre schéma
inchangé, ce qui est la bonne combinaison.

La seconde est qu'il n'y a rien à installer sur le VPS. La base est jointe par le réseau
dans les deux cas ; faire tourner la CLI sur le serveur aurait demandé d'y installer Node
et de l'y maintenir, pour un bénéfice nul.

**2. Le déploiement en production ne s'annule pas en cours de route.** La préproduction
annule un déploiement en cours quand un nouveau arrive — un déploiement dépassé n'a plus
d'intérêt. La production fait l'inverse : un déploiement interrompu peut avoir déjà
appliqué une migration, et l'arrêter là laisserait la base en avance sur le code.

**3. Le crontab est réinstallé à chaque déploiement, en écrasant ce qui s'y trouve.**
C'est délibéré, et c'est la seule façon de garder le serveur et le dépôt d'accord. Une
tâche ajoutée à la main disparaîtrait au déploiement suivant sans que personne s'en
aperçoive ; une tâche retirée du dépôt continuerait de tourner pendant des mois.

Conséquence corrigée au passage : le runbook §11 demandait d'ajouter la surveillance des
ressources à la main. Elle aurait été effacée au premier déploiement en production. Elle
est désormais **dans `deploy/crontab`**, et le runbook dit de ne jamais éditer le crontab
sur le serveur.

**4. La vérification finale utilise le contrôle profond.** Le script de déploiement a
déjà attendu que le conteneur réponde ; la question qui reste n'est pas « un processus
répond-il » mais « le site fonctionne-t-il, base comprise ». C'est la dernière occasion
d'attraper un déploiement techniquement réussi et pratiquement cassé.

**5. Le secret des tâches planifiées est comparé en temps constant.** Un `===` s'arrête
au premier caractère différent, et le temps qu'il met révèle combien du secret a été
deviné ; en le nourrissant caractère par caractère, on le reconstitue. La route refuse
aussi tout secret de moins de seize caractères, et refuse **toujours** si la variable est
absente — une variable oubliée laisserait la route ouverte à tout le monde.

Le secret voyage dans un en-tête, jamais dans l'adresse : une chaîne de requête finit
dans tous les journaux d'accès du chemin.

### Ce qui reste — actions PO

**Rien n'est en ligne tant que `main` n'a pas été fusionnée.** C'est volontaire : la mise
en production est une décision, pas un effet de bord.

1. **Vérifier les enregistrements DNS** — `defi-movember.fr` et `www` doivent pointer sur
   le VPS avant le premier démarrage, sinon Traefik ne peut pas obtenir de certificat.
   Procédure dans `deploy/README.md`.
2. **Renseigner `.env.production`** sur le VPS, dont `CRON_SECRET`
   (`openssl rand -base64 32`).
3. **Ajouter le secret GitHub `SUPABASE_DB_URL`** — sans lui, le job de migrations
   échoue et rien ne se déploie.
4. **Ajouter `https://defi-movember.fr/**` aux Redirect URLs de Supabase**, sinon les
   liens de confirmation envoyés depuis la production retomberont sur la préproduction.
5. **Fusionner `main`** quand tout est prêt.
6. **Éprouver le retour arrière pour de vrai**, une fois qu'il existe deux versions en
   production. Le script est vérifié sur sa logique, pas encore contre un vrai Docker.
