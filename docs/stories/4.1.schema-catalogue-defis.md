# Story 4.1 : Schéma du catalogue et validation des configurations

## Status

Draft

## Story

**As a** organisateur,
**I want** que le catalogue de défis vive en base et refuse les configurations
incohérentes,
**so that** un défi mal réglé soit rejeté au moment où on l'écrit, pas découvert par
400 participants un matin de novembre.

## Acceptance Criteria

1. La table `challenges` porte le catalogue : titre, description, évaluateur, configuration,
   famille de sport, difficulté, points, portée, règles de récompense, activation.
2. Un défi est une **ligne**, jamais du code (architecture D2). Aucun redéploiement pour en
   créer un.
3. La configuration de chaque type d'évaluateur est **validée par un schéma**, à l'écriture
   comme à la lecture.
4. Une configuration invalide est **refusée avec un message exploitable par un bénévole**,
   pas par un développeur.
5. Les sept types d'évaluateurs sont déclarés dans un registre unique, qui pilote la
   validation et l'interface.
6. Le catalogue est lisible par les participants **uniquement pour les défis qui leur sont
   attribués** — le reste resterait un spoiler.
7. Seuls les administrateurs écrivent dans le catalogue.
8. Les points sont un entier positif, borné.
9. La table `challenge_assignments` porte l'attribution d'un défi à un participant pour une
   date, avec son état.
10. Un participant ne peut recevoir deux fois le même défi dans l'édition, garanti par la
    base.

## Dev Notes

**La décision structurante du projet** (architecture D2, NFR18) : le code fournit un
catalogue d'**évaluateurs**, et chaque défi est une fiche qui en choisit un et lui passe des
paramètres. Coder chaque défi individuellement remettrait un développeur dans la boucle
chaque jour de novembre.

**La validation est le vrai livrable de cette story.** Un `jsonb` non validé est une
promesse de panne : un seuil en kilomètres là où le code attend des mètres donne un défi que
personne ne peut réussir, et le défaut ne se voit qu'au moment de l'évaluation. Zod côté
écriture, et **re-validé à la lecture** — parce que la ligne a pu être modifiée en SQL
directement.

**Les messages d'erreur s'adressent à un bénévole.** « `config.min_distance_meters:
Expected number, received string` » n'aide personne. « La distance minimale doit être un
nombre de mètres » est actionnable.

**Le catalogue est un spoiler** (AC 6). Un participant qui lirait le catalogue complet
connaîtrait les défis à venir et pourrait s'organiser — ce qui n'est pas grave en soi, mais
retire tout intérêt à la surprise quotidienne. Il ne lit que ce qui lui est attribué.

### Testing

- Vérifier qu'une configuration invalide est refusée, pour chacun des sept types.
- Vérifier qu'un participant ne lit pas le catalogue complet — **avec deux comptes réels**.
- Vérifier que la base refuse un second exemplaire du même défi pour la même personne.
